# Survey2026 (SurveyApp)

**Survey2026** is an Android survey runtime designed for field use where connectivity may be unreliable or unavailable. It combines structured survey execution, on-device speech recognition, local SLM-based answer evaluation/follow-up generation, persistent diagnostics, and resilient background upload/recovery.

The Android Studio project name is `SurveyNav`; the product/repository name is **Survey2026**.

## What the app does

Survey2026 is not a generic chatbot and not just a digital form. It is a structured Android interview runtime that:

1. Loads a validated survey configuration.
2. Runs a deterministic survey/navigation flow.
3. Accepts typed and optional voice input.
4. Uses local Whisper inference for speech-to-text.
5. Uses a local SLM to evaluate free-text answer quality.
6. Generates follow-up questions only when the configured evaluation requires one.
7. Persists survey state and export artifacts.
8. Queues mandatory survey JSON and the associated V2 recording artifacts for resilient background upload.
9. Recovers pending survey uploads after restart, reboot, app replacement, or network restoration.
10. Preserves separately identified recording WAVs and their question/transcript associations for subsequent review and delivery.

Core survey execution remains usable offline. Network access is used for model/download workflows and configured upload/diagnostic destinations.

## Architecture at a glance

```text
Android UI / Navigation
        |
        v
Survey state + configuration
        |
        +--------------------+
        |                    |
        v                    v
Voice capture           Typed answer
        |
        v
whisper.cpp JNI
        |
        v
Transcribed answer
        |
        +-----------> Local SLM evaluation
                         |
                         +--> accepted answer
                         |
                         +--> follow-up generation when required

Survey Finish / explicit incomplete-session exit (where applicable)
    |
    v
SurveyUploadFinalizer
    |
    v
SurveyUploadWork.reconcile(...)
    |
    +--> WorkManager submission / adoption
    +--> logical-survey duplicate protection
    +--> tracker / uploaded-state checks

Recovery entry points
    |
    +--> normal app startup
    +--> BOOT_COMPLETED
    +--> MY_PACKAGE_REPLACED
    +--> network recovery
    |
    v
SurveyUploadRescheduler.recoverPendingSurveyUploads(...)
    |
    v
PendingSurveyUploads discovery
    |
    v
SurveyUploadWork.reconcile(...)
```

The upload/recovery design deliberately uses shared reconciliation for mandatory survey JSON. The old direct `reenqueuePendingSurveyUploads()` path is not part of the current design. V2 WAV artifacts have separate durable identities and must not be inferred to have uploaded solely because survey JSON is complete. The diagram is a high-level view, not an exhaustive V2 implementation call graph.

## Getting started

### Clone with submodules

```bash
git clone --recurse-submodules https://github.com/ishizuki-tech/Survey2026.git
cd Survey2026
```

For an existing checkout:

```bash
git submodule update --init --recursive
```

### Open in Android Studio

Open the repository root and allow Gradle Sync to complete.

A physical Android device is recommended because the project depends on real microphone, JNI, on-device inference, WorkManager, and lifecycle behavior that are not fully represented by emulator-only testing.

### Safe local build without embedded development secrets

```bash
./gradlew :app:testDebugUnitTest --no-daemon \
  -PskipModelDownload=true \
  -Pdebug.embedSecrets=false \
  -Prelease.allowSecrets=false

./gradlew :app:assembleDebug --no-daemon \
  -PskipModelDownload=true \
  -Pdebug.embedSecrets=false \
  -Prelease.allowSecrets=false
```

Release assembly:

```bash
./gradlew :app:assembleRelease --no-daemon \
  -PskipModelDownload=true \
  -Prelease.allowSecrets=false
```

### Separate local-install identity

To install a locally built APK alongside the normal Survey2026 app, explicitly add
`-PlocalBuild=true`. This changes the application ID to `com.negi.survey.local` and
the app label to `Survey2026 Local` for both Debug and Release builds; builds without
this property retain the normal identity.

```bash
./gradlew :app:assembleDebug --no-daemon \
  -PlocalBuild=true \
  -PskipModelDownload=true \
  -Pdebug.embedSecrets=false

./gradlew :app:assembleRelease --no-daemon \
  -PlocalBuild=true \
  -PskipModelDownload=true \
  -Prelease.allowSecrets=false
```

The normal Gradle `release` build is **not forcibly debug-signed**. `release.useDebugSigning=true` remains an explicit opt-in only. Production release signing is handled separately.

## Survey configuration

Shipped survey configurations:

- `app/src/main/assets/survey_config10.yaml` — English
- `app/src/main/assets/survey_config_sw_10.yaml` — Swahili

The configuration drives the structured survey and the SLM prompt behavior.

### TWO_STEP answer validation

The shipped **Kiambu Q7–Q16** English and Swahili AI nodes use the two-step path where configured. Older Q8–Q17 references are a historical pre-Kiambu numbering convention, not the current questionnaire:

1. **EVAL** — evaluate the respondent answer.
2. Parse strict structured output:
   - `score`
   - `missing_points`
   - `followup_needed`
3. If needed and valid, run **FOLLOWUP** generation.
4. Persist only an accepted, non-duplicate follow-up question.
5. Keep run/survey ownership so cancelled or stale inference cannot update a replacement chain.

Malformed or contradictory evaluation output fails closed.

ONE_STEP support remains available for configurations that use it, but it is not the active Kiambu Q7–Q16 baseline.

Real-model semantic quality is intentionally tracked separately from deterministic app correctness. See [TODO.md](TODO.md).

## Survey upload and recovery

### V2 artifact naming and per-recording identity

The current V2-only storage contract, integrated through [#155](https://github.com/ishizuki-tech/Survey2026/issues/155), uses a canonical **UUIDv7 survey ID** and the **survey creation time encoded in that UUID** as its common UTC timestamp. `V2ArtifactPaths` constructs survey-bound paths. Each artifact's path is relative to the **root of its configured export repository**, with **no leading `exports/` prefix**. Production uses `SurveyExports`; development uses `SurveyExports-Dev` according to configured routing. This is a clean-install V2 contract; it does **not** migrate prior on-device V1 state.

```text
YYYY-MM-DD/
├── survey/
│   └── <StartUTC>_survey_<Device>_<SurveyUUIDv7>.json
├── voice/
│   └── <StartUTC>_voice_<Device>_<SurveyUUIDv7>_<QuestionID>_<RecordingID>.wav
└── diagnostics/
    ├── survey/
    ├── whisper/
    ├── slm/
    ├── logcat/
    ├── runtime/
    └── crash/
```

`<StartUTC>` has the format `YYYY-MM-DD_HH-mm-ssZ`. The date directory comes from that survey-start UTC value, **not** from the upload attempt date. Question IDs are filename-safe or converted to a stable hashed segment when necessary. Standalone diagnostics can use their actual event time and a `no-survey` name. Historical V1 examples containing `exports/` belong to **old field evidence only**; do not use them as V2 examples.

Per-recording preservation ([#138](https://github.com/ishizuki-tech/Survey2026/issues/138)) gives **each valid captured WAV**, including re-recordings, its own stable recording identity and upload/recovery reference. Its associated exact question or follow-up text and **Whisper transcript** are kept distinct from later user-edited answer text. Survey JSON success alone does **not** establish that every referenced WAV was delivered: check the corresponding recording artifacts and recovery evidence. These are implementation and recovery invariants, not a claim that every current V2 device scenario has completed field acceptance.

### Mandatory JSON recovery and historical validation

Survey JSON is the mandatory survey artifact.

The current design uses logical survey identity rather than only file-path identity. The recovery layer:

- groups pending artifacts
- selects a canonical candidate
- reconciles against WorkManager state
- checks tracker state
- checks uploaded state
- suppresses duplicate logical submissions
- preserves retry/recovery semantics

Current recovery classifications include:

- `SUBMITTED`
- `ACTIVE`
- `SUBMITTED_TRACKER_UNCONFIRMED`
- `ALREADY_UPLOADED`
- `DEFERRED`
- `INVALID`
- `OPERATIONAL_FAILURE`

Historical V1-era acceptance evidence on Pixel 9a / Android 16 (the described runs do **not** by themselves certify the later V2 protocol):

- offline pending recovery
- network restore -> upload
- reboot recovery
- app-update / `MY_PACKAGE_REPLACED` recovery
- duplicate suppression
- post-success cleanup / no re-submit

Direct app-side `LOCKED_BOOT_COMPLETED` logging remains a validation observation point rather than a claimed completed result.

## Secret handling

Do not commit:

- release keystores
- keystore passwords
- GitHub tokens
- Hugging Face tokens
- other credentials
- generated signed APKs unless intentionally published as release artifacts

Debug builds can embed development credentials only when explicitly enabled.

The Hugging Face token transport path uses AES-GCM material rather than storing the plaintext token directly in BuildConfig. Because decryption material is also delivered with the application, this is **APK-obfuscation / plaintext-avoidance**, not a secure secret-storage boundary against a determined APK analyst.

Release builds only allow embedded runtime credentials when `release.allowSecrets=true`.

Check the survey-specific recovery/reconciliation logs first. Do not infer survey failure only from generic diagnostic worker errors.

Relevant components:

- `PendingSurveyUploads`
- `SurveyUploadRescheduler`
- `SurveyUploadWork`
- `SurveyUploadWorkTracker`

### Upload deferred after retry exhaustion (Issue #128)

The uploader permits five in-process HTTP 409 create attempts; the Worker permits
five attempts per batch. Existing startup/recovery scans can schedule one final
batch after exhaustion. A second exhaustion stops automatic rescheduling; a
verified permanent content collision is deferred immediately. A restart does
not reset this budget. Survey JSON still uses Issue #86's shared canonical
reconciliation, uploaded ledger, and execution authority. A new diagnostic
capture may be scheduled on startup; it is separate from an older deferred capture.

For operator investigation:

1. Identify the exact installation/package and collect its logs. Look for
   `Upload conflict exhausted`, `Upload deferred after conflict exhaustion`,
   `Conflict-deferred artifact retained`, and survey reconciliation's
   `DEFER_CONFLICT_EXHAUSTED`. WorkManager work has tag `github_upload`; inspect
   its state and output Data key `error` where developer tooling is available.
   An initial failure can still have recovery pending; `FAILED` alone does not
   prove final exhaustion or that the remote write never succeeded.
2. With authorized access to that installation's private storage, preserve
   `files/upload_conflict_recovery/*.properties`. Each filename is the SHA-256
   of its logical `key`: `survey:<normalized-id>`, `file:<absolute-local-path>`,
   or `capture:<original-worker-UUID>`. `exhausted=1` marks the initial exhausted
   batch; `exhausted=2` marks final deferral, also used for permanent collisions.
   For non-survey artifacts, `dispatched=true` means the recovery request was
   acknowledged/found, not that upload succeeded. `recoveryId` identifies that
   request. Survey recovery instead uses the existing survey work tracker.
3. Preserve the retained bytes and metadata together. The record's `input` is
   Base64-encoded WorkManager Data, **not JSON**. It retains owner, repository,
   branch, path prefix, file/path or session identity, capture UUID, UTC date,
   and survey protocol where applicable; the token is excluded and credentials
   are resolved again. File-mode artifacts are located by `filePath` in this
   Data, including WAVs under `files/pending_uploads_shared/voice/<survey>/` and
   survey JSON under `files/pending_uploads/`. Worker-generated diagnostics are
   under `files/diagnostic_captures/<original-worker-UUID>/{logcat,runtime,ring}/`;
   keep hidden `.complete`/`.retain` files and `files/diagnostic_capture_dates/`.
   Preserve relevant survey route/tracker/ledger state when investigating JSON.

On an authorized **debuggable** installation, Android's existing `run-as` access
can list the directories without changing them, for example:

```bash
adb -s SERIAL shell run-as PACKAGE ls -la files/upload_conflict_recovery
adb -s SERIAL shell run-as PACKAGE ls -la files/diagnostic_captures
```

For preservation, use `adb -s SERIAL exec-out run-as PACKAGE tar -cf -` followed
by the **existing** relative directories identified above, redirecting the
archive to a protected host file. Missing directories are normal for unused
modes; inspect first. Treat captured respondent data and logs as confidential.
Release installations may reject `run-as`; there is no built-in export for this
state, so escalate through authorized device support rather than clearing data
or replacing the installation to gain access.

If only the initial batch is exhausted and the final recovery has not already
been dispatched, correct connectivity/credentials for the **original destination**,
then reopen the app to invoke existing recovery.
The optional-artifact replay requires matching captured routing; survey JSON
continues through canonical reconciliation. Create-only comparison may accept
matching remote content after ambiguous success, but rejects unrelated content.
Inspect the recorded recovery WorkInfo or survey tracker and ledger afterward;
records remain after success, so their existence alone does not prove a pending
upload. An already-dispatched optional-artifact request is not recreated.

**There is no supported operator reset or manual resubmit operation after final
deferral.** Preserve the evidence and escalate for a separately reviewed repair.
Do not delete/edit exhaustion records, WorkManager state, survey authority,
routes or uploaded ledgers; rename/move staged files to evade suppression;
overwrite remote content; or uninstall/clear app data to force another attempt.
Restart/reboot is not a final-deferral reset.

Deferred captures have no age/size eviction policy. Successful captures are
removed during later recovery scans only when committed WorkManager success is
still observable, and explicit `.retain` prevents that cleanup. Missing success
history also retains bytes. Captures, exhaustion records and date metadata can
therefore accumulate indefinitely; monitor storage and preserve evidence before
requesting an authorized cleanup. This procedure documents that limitation and
does not add a recovery UI, reset command, or retention policy.
